# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

DungeonScrawl is a typing roguelike, originally built for Ludum Dare. The player moves, attacks, and loots by typing words shown next to directions, enemies, and chests. It is a 2D Unity project on **Unity 6000.4.10f1** (see `ProjectSettings/ProjectVersion.txt`).

**Start with `NEXT_STEPS.md`**: where the work stands, what still needs checking by hand, and what to do next. Keep it up to date as work lands.

## Commands

The `unity` CLI is installed, and the project includes `com.unity.pipeline`, which lets the CLI drive a running Editor.

```sh
unity open .                                   # open the project with the matching Editor version
unity status                                   # list connected Editors
unity recompile --project-path .               # compile scripts in the running Editor and report errors (the fastest compile check)
unity build . --target StandaloneWindows64 -o Builds/DungeonScrawl.exe   # batch-mode player build (Builds/ is gitignored)
```

The Unity Test Framework package is installed, but there are no test assemblies or tests. There are no `.asmdef` files, so all game code compiles into `Assembly-CSharp`. The `*.csproj` and `*.slnx` files at the root are generated by Unity and gitignored, so don't edit them.

## Layout

- `Assets/Scripts/` holds the game code. Namespaces mirror the folder path, e.g. `ECS.Systems`, `Utilities.Game.ECSCache`, `UI.Hint`.
- `Assets/Imported/` holds third-party code: RogueSharp as source (re-namespaced to `Imported.RogueSharp`) and DOTween (`DG.Tweening`) as DLLs.
- `Assets/Scripts/Tiles/` holds the two autotiles the dungeon is painted with: `FloorTile` (47-case blob autotiling with slab variants) and `CliffTile` (the rock face under a floor's south edge). Their assets are in `Assets/Prefabs/Tiles/`.
- `Tools/PixelArt/` generates the tiles, the hit/death effects, the creatures' idle frames, the menu backdrops, button frame and volume icons, the in-game interface art, and a pixel font for TextMesh Pro as code (Python + PIL), and slices them in the open Editor. See its README. Every other sprite is hand-made art under `Assets/Graphics/` and `Assets/Resources/Sprites/`.
- `Tools/Audio/` generates the typing, footstep, death and menu sounds, the two music themes and the cave ambience as code (a small chiptune synthesizer in plain Python) into `Assets/Audio/`. See its README. The other effects in `Assets/Audio/` are the hand-made originals.
- `Assets/Resources/Words/{adjectives,nouns,verbs}.txt` are the word lists, loaded via `Resources.Load`.
- `PR/` holds the screenshots and GIFs used by `README.md`. It sits outside `Assets/`, so Unity doesn't import it.
- `Tools/Probe/` inspects and drives a playing Editor from the command line (scene, music, prompts, typing, win/lose, pause menu, screenshots). See its README, including the clean-up after testing.
- Build scene order: `SplashScreen` → `MainMenu` → `Game` → `GameOver` / `Victory`. Scenes are loaded by string name via `SceneManager.LoadScene`. `Victory` started as a copy of `GameOver` and shares its layout (title, run report, two buttons side by side), so change both together.

## Architecture

### Hand-rolled ECS (not Unity DOTS)

- **Entity** (`ECS/Entities/Entity.cs`) is a plain C# object that holds a list of `IComponent`. Each one is owned by an **Actor** MonoBehaviour, which comes from the object pool. `Actor.Enable()` creates a fresh `Entity` every time the actor is pulled from the pool.
- **Blueprints** (`ECS/Entities/Blueprint/`, `IEntityBlueprint`) define an entity type's component set in code. To add an enemy type, write a new blueprint and spawn it from the per-level `SpawnLevelNActors()` methods in `ActorSpawnerSystem`.
- **Components** register themselves in `ComponentCache` in `OnAdd()`. There are two kinds:
  - *Specific* components (`GridPositionComponent`, `RenderComponent`, `ChaseTargetComponent`, …) are cached and looked up by concrete type: `entity.GetComponent<T>()` and `ComponentCache.Instance.GetCached<T>()`.
  - *Generic* components (`IntegerComponent`, `BooleanComponent`) carry a `ComponentType` (`Health`, `Damage`, `Reach`, `FieldOfView`, `Turn`). Look them up with `entity.GetComponent<T>(ComponentType)` or `ComponentCache.Instance.GetCached(ComponentType)`. Plain `GetComponent<IntegerComponent>()` returns whichever one comes first.
  - The `GetCached(...)` overloads return `null`, not an empty collection, when nothing of that type is registered.
- **Systems** are MonoBehaviours on child GameObjects of the `Systems` object in `Game.unity`. In `Awake`, `Systems.cs` collects them **in hierarchy child order**. It runs `IInitializeSystem.Initialize()` in `Start`, and `IExecuteSystem.Execute()` in `Update`, but only while `GameController.IsPlaying`. Every child must implement `ISystem`, or `Awake` throws. The current order is significant:
  `InitializeSystem` (DOTween init) → `WordSystem` → `MapSystem` → `ActorSpawnerSystem` → `TurnSystem` → `MoveSystem` → `RenderSystem` → `AttackSystem` → `ItemSystem`.
  Blueprints call `MapSystem.GetRandomAvailableTile()`, so the map must exist before spawning. `TurnSystem.Initialize` needs the spawned `Turn` components to exist already. To add a system, add a child GameObject in the scene at the right position.
- **Singletons**: `MonoSingleton<T>` finds the scene instance lazily with `FindAnyObjectByType` and logs an error if there is none. `MonoSingletonCreateIfNull<T>` creates the instance instead. Both are scene-scoped. `ComponentCache`, `ActorCache`, `MapSystem`, `GameController`, `HintCache`, and `ObjectPools` are all singletons.
- **Pooling**: `ObjectPools.Instance.GetPooledObject<T>()` keys pools by type, and the pools are configured in the inspector. Actors, `TextPopup`s, fireballs, explosions, and `Effect`s (hit sparks, death puffs) are pooled.

### Gameplay loop

- `InputController` reads `Input.inputString`, which belongs to the **legacy Input Manager** (`activeInputHandler: 0`). Switching to the new Input System alone would break typing.
- Each typed letter goes to every `SpellHint` in `HintCache`. A hint that reports `WordComplete` submits the input. If every hint reports `WordWasInvalid`, the input buffer resets.
- Every key answers. A letter that fits blips one step higher than the last (`AudioPlayer.PlayLetter`) and hops the prompts it fits (`SpellHint.Bump`). A finished word chimes. A wrong letter buzzes, and the prompts it broke flash red and shake (`SpellHint.Reject`). A letter that breaks the word under way but starts another word switches to that word instead (never to a single-key move, which mid-word is more likely a slip).
- `InputController` maps words to actions in three dictionaries: movement (four directions, shown by `MoveHints`), attack (one word per enemy), and loot (per chest).
- Word lengths: movement 3, attack `3 + CurrentLevel`, loot 9. With nothing hostile in sight (`UpdateMovementType`), the move prompts become single keys: W/A/S/D by default, or a random letter per direction. The player picks with the button in the main menu's bottom-left corner (`MoveKeys`, saved under `"MoveKeys"`). With WASD on, attack and loot words never start with W, A, S or D (`MoveKeys.Blocks`), so a quick move can't swallow the first letter of a word. Quick moves go by presses: `InputController` ignores the OS repeats of a held key while their prompts are up and no word is under way. `WordSystem` buckets the word lists by length (3–9) and recycles words once a bucket runs out.
- Turn model: the player has **no** `Turn` component and can act at any time. The player's first action sets `GameController.PlayerHasMoved`, which is only reset at level end. From then on, `TurnSystem` cycles enemy `Turn` flags on a timer (`0.4s / difficulty`), so play is effectively real-time after the first move.
- `MapSystem` generates the level with RogueSharp `RandomRoomsMapCreationStrategy`, paints the `Tilemap` with `FloorTile` and `CliffTile`, and provides walkability checks and pathfinding (`GetMoveDirection`) for the chase AI in `MoveSystem`.

### Rendering

- **Pixel scale**: `PixelPerfect` picks whole-number zooms from the screen height: `Zoom` for the world (about 10 tiles tall; 7x at 1080p) and `UiZoom` for the HUD (4x at 1080p, as it was laid out). `PixelCamera` sizes the camera only when the screen size changes, so the level transitions can still tween `orthographicSize`. `PixelCanvas` scales the HUD and menu canvases, which are laid out at 4 canvas units per art pixel (1920x1080). The menus' Munro fonts import as hinted raster, so they stay hard-edged, and their sizes are multiples of 10.24 (one font pixel per 10.24 points).
- **Light**: the player carries the light. `MapSystem.GetLight(cell, position)` returns a warm colour fading with distance for cells in view, a dim blue for explored cells, and clear for unexplored ones. `RenderSystem` moves the light with the player's sprite (with a slight flicker), fades tiles toward their light in `MapSystem.UpdateTileLighting`, and tints actors. `Chest` and `Door` tint themselves the same way. Alpha 0 still means "not drawn", which the Scrawler bot relies on.
- **Idle animation**: `RenderComponent.Sprite` is a creature's identity sprite. `RenderSystem` draws the current frame of its loop from `Sprites.GetFrame`, using the `_animations` list on the `Sprites` object. Classify creatures by `RenderComponent.Sprite`, not `Renderer.sprite`.
- **Feedback**: `AttackSystem` blinks the target white (`SpriteFlash`, which needs the `DungeonScrawl/Sprite Flash` shader on the actor material), jolts its sprite, spawns a hit spark, puffs smoke on death, and shakes the camera (`CameraMovement.Shake`) when the player is hurt. Creatures face the way they move; sprites are drawn facing left.
- **Interface**: everything in-game speaks the menus' language (ink outline, cream frame, gold rivets, dark plum face) at one pixel per art pixel.
  - Prompts (`SpellHint`, also the move hints) are 9-sliced plaques that `FitBox` sizes to their word on whole art pixels, with the icon inside on the left. Typed letters turn gold. The move hints sit round the player at 1:1 (`MoveHints` used to be at half scale).
  - All in-game text uses `MunroSmall Pixel`, a bitmap TextMesh Pro font built by `Tools/PixelArt` (font size 1 for the UGUI prompts, 10 for world-space popups, 20 for announcements). Keep its texts at normal weight: bold adds a pixel of spacing and padding. `TextPopup` draws an ink outline from four copies of its text.
  - TextMesh Pro gotcha: an old prefab can keep the legacy `m_textAlignment` field, which overwrites the alignment on every load until it is set to 65535 (converted).
  - The status panel (top-left of the `Game` canvas) is laid out at 4 canvas units per art pixel, like the menus: hearts, then power and light gems, each a `GameResource` with full and empty sprites.
- **Pause and options**: Escape during a level opens `PauseMenu` (resume, options, quit to title). `GameController.SetPaused` stops time (`Time.timeScale = 0`) and `InputController` ignores typing meanwhile, so everything on the pause canvas tweens with `SetUpdate(true)`. `OptionsMenu` sets music, sound and the quick-move keys, the same settings as the main menu's corner buttons; the arrow keys work too. `ButtonFeel` gives these buttons their hover and selection feel on unscaled time.

### State across scenes

- The `Game` scene is reloaded for each level. `GameController.CurrentLevel` is a static field that survives the reload. There are 5 levels, and finishing level 5 wins the game: a "-CONGRATULATIONS-" popup, then the `Victory` scene.
- `RunStats` is static for the same reason. `GameController` starts it on level 1 and finishes it on death or the win; `InputController` and `AttackSystem` feed it letters, mistakes, words, chests and kills. Typing speed only counts the gaps between letters of a word, and drops gaps over 1.5s. The single-letter move prompts shown when nothing hostile is in sight are steering, not typing: those keys, and stray keys while they're up and no word is under way, count towards neither speed nor accuracy. The score is (letters of finished words + 25 per kill + 50 per chest + 250 per level cleared) times the difficulty; the best is kept in `PlayerPrefs` under `"BestScore"`. `UI.RunReport` tallies it all up on the game over and victory screens.
- Player stats carry over between levels through `PlayerPrefs`, keyed by the `ComponentType` name (see `Player.SavePlayerStats` / `ClearPlayerStats`). `PlayButton` stores difficulty under the `"Difficulty"` key. `SplashScreenTweener` resets both at the start of every run, but leaves the volume settings (`Sound.Volume`, keys `"MusicVolume"` and `"SoundVolume"`) and the best score alone. Don't go back to `PlayerPrefs.DeleteAll()`.
- `Sound.Jukebox` is the one object that outlives a scene. Each scene has a `Jukebox` naming its music and ambience; the first to wake persists (`DontDestroyOnLoad`), and later ones hand it their tracks and destroy themselves, so music never cuts on a scene load or level reload. `GameController` fades the music out on game over and over to the title theme on a win.
- `Constants.GetRandomSeed()` returns the current UTC millisecond, so map and word generation differ every run. The `Constants.RandomSeed` constant is unused. For reproducible runs, change `GetRandomSeed()`.

### Testing shortcuts

In the Editor and development builds (`Debug.isDebugBuild`), while a level is being played, F9 wins the run on the spot and F10 loses it (`GameController.Update`). The stats so far go to the victory or game over screen.

## Conventions

- Follow the StyleCop rules in `Settings.StyleCop`. Put `using` directives inside the namespace. Name private fields `_camelCase` and expose them to the inspector with `[SerializeField]`.
- Most source files start with the same license/copyright header block. Keep it when creating files alongside existing ones.
- Animations and UI transitions use DOTween (`DOFade`, tweeners under `UI/Tweeners/`). Don't add a second tweening approach.
